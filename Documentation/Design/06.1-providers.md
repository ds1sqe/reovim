# 06.1 — Resource, State Model, Domain and Representation providers

A [Kernel module](06-modules.md) contributes through public provider
contracts. Source directories group responsibilities; they do not restrict
registration to implementations compiled into Kernel.

| Provider | Public contribution | Execution owner |
| --- | --- | --- |
| Resource | Create/open subjects and supply their typed access interfaces | Kernel Runtime and granted Resource/Host adapter |
| State Model | Initial values, immutable working state and prepared state transitions | Kernel Runtime, outside Core commit authority |
| Domain | Semantic values, operations and validation | Kernel Runtime through the selected semantic provider |
| Representation | Observe Buffer state and lower qualified semantic edits | Kernel Runtime through the selected interpretation provider |

Client extensions register with their own Client APIs. Kernel neither imports
those contracts nor executes their input/rendering behavior. A semantic
Representation can produce structured preview data; [Clients](04-clients.md)
render it. Optional [Client exports](07.3-client-resources.md) use granted
Resource proxies without entering the Kernel module lifecycle.

## Registration

Registration supplies an exact [Contract](01.2-resource-access.md) and an
executable provider through the [adapter tables](05.1-composition.md). Caller
access selects Runtime, instance, scope and allowed contributions. Validate
family/schema, compatibility and grants before accepting ownership; rejection
leaves the supplied provider with its caller.

| Provider control | Behavior |
| --- | --- |
| register(contract, provider) | Accept ownership; return an exact registration Resource |
| unregister(registration) | Fence new use; await drained registration or reject busy |

A provider carries executable access and required code/data ownership, not
just a name. Native/linked adapters supply tables; service adapters supply a
proxy. Conflicting active selections reject; dependency declarations govern
selection, never registration order.

During activation, successful registration prepares a provisional owned
contribution. Lookup exposes it only when the module becomes Ready. Failed
activation removes its provisional registrations through the same owner.
Accepted registration retains the provider even if the caller drops its
wait; Runtime owns completion and cleanup.

Unregister stops new access, while existing uses keep the implementation
alive. Success means its registration lifetime has drained. Persistent users
requiring continued access return busy before removal; use explicit
close/detach or an agreed migration. Module unload follows
[modprobe](06.2-modprobe.md); it cannot free code by removing a tree name.

## Provider access and composition

```text
sftp module:
  register a Resource factory -> open a subject -> read-at/publication requests

markdown module:
  import the selected model's public state access and Text API
  register Markdown semantics and source/preview Representations
  attach Representation -> observe -> submit a qualified semantic edit
// Independent modules may provide each part through compatible contracts.
// The chosen Resource/model need not be a file or byte-addressed state.
```

Providers declare supported model/semantic contracts, required imports,
output ownership, cancellation, failure and cleanup. Runtime checks actual
compatibility; matching names or Rust types alone do not establish it.
Representations consume public Domain/model APIs, never a concrete provider's
private storage. Shared payload types belong in their component API.

An access interface defines its own cursor, message or position semantics:

```text
stream read       // Ordered consumption; cursor/competition belongs to access.
read-at(position) // Random access in the interface's declared units.
receive message   // Message boundaries and loss behavior remain explicit.
command write     // One complete request; its result belongs to that request.
semantic edit     // Domain-qualified values, not a universal byte offset.
// A Resource can offer several interfaces; support and grants are separate.
```

## State Model and Core boundary

Extending a Domain over an existing model does not require new storage.
A new working-state structure needs a State Model provider. Its `Initial`
type owns valid initialization; [Buffer](02-buffer.md) owns creation and
the resulting Buffer/History lifetime.

```text
Runtime captures current Buffer state, selected History edge and provider
  -> provider reads retained immutable state through its public contract
  -> provider validates and prepares a new immutable candidate
  -> Runtime checks ownership, model compatibility and reserved installation
  -> Core revalidates currentness/grants/edge; installs state + History
  -> Runtime releases unused or retired values after leaving Core authority
// Preparation may fail or complete later; rejection preserves state/History.
// Core performs no provider callback or fallible work after the commit cut.
// Undo/Redo preparation obeys the same boundary; no stored undo callbacks.
```

The candidate must retain all backing and code needed for its data and
destruction. Acceptance transfers that ownership to Buffer/History. Candidate
preparation cannot mutate the installed state; a borrowed or partially
resident value must remain valid through its declared lease.

Core needs a model-independent owned state boundary, with exact preconditions
and installation authority. It does not interpret arbitrary semantic payloads
or dispatch module code under its state lock. Ordinary editing modules submit
[semantic edits](03.1-representation.md), not candidates or Core commands.

The exact provider-family tables and prepared-state/History ownership types
are still undefined and must be specified before implementation. Their
design must demonstrate a new non-text, non-byte-addressed model loaded into
the same running Kernel; generic source examples alone do not establish that.

## Lifetime evidence

```text
Resource access     -> may retain endpoint/provider and borrowed storage
Representation     -> may retain interpreter, observations and pending edits
Buffer/History     -> retain model/data/code needed by accepted states
Session snapshot   -> retains code only if its stored form requires that code
request result     -> retains code required to read or destroy the result
// Removing a provider cannot invalidate any of these existing obligations.
```

The [worked journey](07.1-module-journey.md) shows how these ownership rules
keep a model loaded while a Buffer or its History still needs it.
