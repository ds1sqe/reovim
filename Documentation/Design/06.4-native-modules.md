# 06.4 — Native modules and service adapters

New Resource, State Model, Domain and Representation implementations must
load into an already running Kernel without rebuilding or restarting it.
The native boundary is a language-independent versioned C ABI. The Rust SDK
wraps it; a C module or host can implement the same contract directly.
The initial native tables are declared in [Interface ABI][abi-types] and the
[C header][abi-header]; [Rust adapters][rust-sdk] wrap both sides. Module v2
receives optional caller-v1 Kernel imports and declares unload
readiness. Native models currently use synchronous preparation and immutable
retained states; asynchronous provider tables remain incomplete.
[The overview](00-overview.md) describes compatible Clients, Kernels and hosts.

```text
Rust Kernel module -> Rust SDK -> native module ABI -> Kernel Runtime access
C Kernel module  -------------> native module ABI -> Kernel Runtime access
service module -> versioned protocol adapter -> Kernel Runtime access
// Both enter the public lifecycle/provider contracts under their own grants.
// Host adapters own library/process loading; portable Kernel stays no_std.
```

The Rust ABI has no stability guarantee; ordinary Rust generic tables and
trait objects cannot establish an independently built plugin contract.
[Rust ABI reference][rust-abi]. The native contract is specific to its admitted
platform/ABI version. Compatibility with arbitrary Kernel versions, platforms
or editor plugins is not implied.

## Required binary boundary

| Boundary | Required contract |
| --- | --- |
| Entry point | Versioned factory, descriptor layout/extent and exact supported ABI |
| Imports/exports | Contract name/version, table layout, owning instance and scope |
| Context | Opaque owned handle with explicit lifetime; no concrete Runtime/Core type |
| Values | Defined field layout, widths, extent and schema; no Rust-owned collections across ABI |
| Ownership | Borrow duration, transfer point, retain/release and allocator-specific destruction |
| Calls/results | Admission, pending work, cancellation, errors, uncertainty and cleanup |
| Execution | Thread/reentrancy rules, readiness/wakeups and no unwinding across ABI |

Keep Rust `Box`, `String`, `Vec`, Rust-specific reference lifetimes and
trait-object layouts behind the SDK adapter. A byte transport encoding does
not make every Resource byte-addressed.
The [common Message](01.2-resource-access.md) preserves contract/version, data
and reference slots. Adapters translate references with their declared use and
ownership; module codecs handle domain values. Futures stay inside adapters.

Copy admitted metadata into owner storage or retain its code/data lifetime.
A string or destructor inside a library does not remain valid after unmap,
even if the Rust source declared it static. Data returned across the boundary
must name its matching release mechanism; the other side cannot guess which
allocator owns it.

The current caller profile is single-threaded; wake references are thread-safe.
Connection and pending-call references have matching release callbacks. Request
inputs are copied before return; terminal views live until pending-call release.
Polling observes results; only the implementation owner advances execution.
The native Resource provider profile currently settles callbacks synchronously.
These initial profiles do not establish complete module lifecycle conformance.

Module factories construct inert contexts. They may resolve granted metadata,
but cannot start Kernel work before registration. Stored imports retain their
connection through its own table. Unload readiness runs outside registry guards
with new provider requests fenced. Readiness leaves the provider usable until
its owner commits removal; another contribution can still return busy. A module
cannot report ready while work or wake references still require its code.
Root shutdown retries eligible providers so a module can adopt a dependency's
settled result before that dependency is removed.

## Load and release

```text
inspect passive declaration      // No provider activation or installation.
validate policy/dependencies     // Capture exact versions, scopes and grants.
Host loads admitted artifact    // Loader initialization may execute code.
check binary interface          // Reject incompatible tables before dispatch.
construct instance + drive it   // Module factory and lifecycle, outside Core.
publish ready providers         // Only after required activation succeeds.
```

Native loading itself is an execution boundary: platform library constructors
may run before entry-point validation; see [dlopen initialization][dlopen].
Passive catalog inspection never loads a library. Failed load/activation
keeps any required cleanup owned; an error is not proof that no code ran or
that unloading is already safe.

[modprobe](06.2-modprobe.md) owns dependency reuse, provisional rollback and
unload admission. Removing registrations stops new users; code remains mapped
until calls, callbacks, instances, data leases and result destructors that
need it have finished. Persistent state can report busy. Replacement creates
a new instance; old access never dispatches to the replacement by alias.
Unloading one instance releases only its own use of the artifact. Other
instances or native-loader references may retain the mapping. Closed reports
the completed instance lifetime, not disappearance of every code page.

Session state may survive code unload in a declared versioned data form whose
retention/destruction is independent of that implementation. Restoration
requires a compatible schema or explicit migration. Module-private live
objects are not automatically persistent or portable.

## Service and language adapters

Kernel service adapters can host language implementations outside the native
loader. Client extension adapters belong to their respective Client contracts.
Follow the [SDK/family matrix](../README.md): Python/TypeScript service surfaces
and process ownership remain separate from the native Kernel module ABI.
Native library loading is not the Web extension mechanism; no embedded
interpreter is selected. Building a TS GUI does not implement its extension SDK.
The service profiles still need exact codecs, reference translation,
negotiation, correlation, recovery and lifecycle rules, independently of the
native tables.

Client Runtime owns user input, views, rendering and user-facing output for
every language. Kernel-facing adapters carry semantic calls and observations;
they do not move Client rendering into Kernel. Resource I/O and execution
control retain their own Host contracts and grants.

Grants are not an in-process memory/crash sandbox. Native modules are trusted
code in their execution host. Service isolation/termination requires separate
evidence. No module callback or destructor runs under Core commit authority.

## Loading into a running Kernel

Build Kernel once; start it, then build an admitted module against the public
SDK/ABI without rebuilding Kernel. Load it, exercise its provider through
public APIs, release dependants and unload while Kernel continues serving
unrelated work. Test incompatible binaries, missing dependencies, failed
activation, retained data/results, busy unload and replacement generations.

An added State Model must complete edit/Undo through the same Core authority.
Compilation, entry-point discovery or a command-only module is insufficient
evidence for that boundary. [Providers](06.1-providers.md) owns the data and
History lifetime requirements.

Conformance must also exercise independent implementations: a protocol Client
against compatible servers, and the same native module artifact against
compatible module hosts. Include C ABI providers/consumers with no private
Rust dependencies. These probes establish only their exercised boundaries;
loading a test artifact does not qualify a complete alternative Kernel.
