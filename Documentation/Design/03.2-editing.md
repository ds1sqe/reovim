# 03.2 — Editing operations

[Buffer](02-buffer.md) defines working state and access;
[History](02.1-history.md) defines accepted transitions and Undo/Redo.
An edit changes that state through an ordinary Resource request.
[Request recovery](01.3-requests.md) also applies to creation, loading and I/O.

A [qualified semantic edit](03.1-representation.md) names what to change and
the exact interpretation/state it used. Runtime prepares that change; Core
installs it together with the corresponding History step.

## Atomic installation

The commit cut begins the infallible installation of state and History.

```text
semantic intent + observed state
  -> Runtime: authorize, prepare and validate outside Core authority
  -> Core: recheck currentness, grants and the selected History edge
  -> commit cut: install working state + History atomically
  -> Runtime: release retired state/candidates outside Core authority

// Rejection changes neither state nor History.
// After the cut, under Core authority: no I/O, wait, callback or fallible step.
// Clients submit semantic edits, never native plans, nodes or executor jobs.
// Source observation is read-only; an accepted import uses this edit path.
```

[Provider preparation](06.1-providers.md) defines the State Model/Runtime
boundary and ownership needed by dynamically loaded implementations. Only
that authorized provider path supplies candidates; ordinary modules call the
semantic edit API. Core performs no user input handling or rendering.

The first profile accepts one transaction per History step. Grouped typing,
dragging and painting still need defined intermediate feedback, peer
visibility, confirm/cancel behavior and an Undo unit. Grouping Buffers creates
no cross-Resource transaction.
[History](02.1-history.md) owns branching, edge selection and retained
inspection.

Accepted changes report exact request/state/transition. Client cursor,
selection and follow policy do not gate acceptance. Domain positions can name
time, image layers or disjoint JSON paths.
[Semantic values](03.1-representation.md) own qualification and translation;
authored masks/styles are content, while zoom and computed layout are Client
policy.

## Publication is explicit

```text
edit / Undo / Redo  -> local Buffer + History
save               -> publish selected state to retained backing/base
export             -> publish to a separate destination; keep backing
Save As            -> publish, then conditionally associate the new backing
rename             -> change locator only with proof of preserved identity

// Undo cannot retract a network send, hardware action or settings activation.
// Saving restored state requests a new external effect.
// Following state never triggers save. One-shot send/pulse uses its own API.
```

[Publication](03.3-publication.md) owns captured data/base, conflicts, effects
and Save As outcomes. Settings activate at their owner's publication
acceptance. Saving a draft into another Buffer invokes that Buffer's
acceptance/History; each hop checks grants and preconditions and does not save
the next backing. An immediate control may compose edit then publication and
retain both outcomes.
