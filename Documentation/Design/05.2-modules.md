# Kernel modules and SDKs

A Kernel module contributes services/providers through public Kernel and
component contracts. Kernel Runtime owns its activation and execution, whether
embedded or served remotely. This chapter's Module API and modprobe describe
Kernel modules. A Client module is an extension under its own
[Client contracts](04-clients.md), with a separate loader/lifecycle. It can
logically depend on Kernel services through [composition](05.1-composition.md).

| Term | Meaning |
| --- | --- |
| Package | Distribution containing code and passive declarations |
| Declaration | ModuleId, package metadata, exact imports/exports and bounds |
| Module instance | Activated implementation owned by one Kernel Runtime |
| Provider | Implementation of one public contribution contract |
| Module registry | Passive availability and declarations, separate from instances |
| modprobe | Resolve dependencies, load and activate a named Kernel module in scope |

Code loading, execution, state scope and namespace are distinct. A host can
load code once for multiple instances with independent state and grants.
Registry views, instances and retained state use Resource identity.
A ModuleId is a nonzero opaque 16-byte package key supplied by its manifest.
It is separate from ApiId and the Resource identity of an activated instance.
The [resource tree](01.1-namespace.md) names them without owning their
lifetimes. [Composition](05.1-composition.md) owns imports and wiring.

Passive package metadata pairs ModuleId with a nonempty ASCII name (at most
255 bytes), a nonzero u32 declaration revision and supported scopes. The scope
mask uses Global=1 and Session=2; it conveys no grant. Registry selection pins
an exact revision rather than inferring compatibility from a name or path.

A declaration holds at most 256 dependency selections. Each names a ModuleId,
exact revision, Same or Global scope, and whether absence is optional. Same
uses the requesting instance's Global or exact Session scope. Global explicitly
requests shared state. Duplicate package/scope selections reject; optional
absence requires the module's declared fallback. Metadata alone constructs no
instance. [modprobe](05.3-modprobe.md) owns graph validation and activation.

Each dependency can request exact exports with `module::Import`: a local ASCII
name, relative export path, complete API declaration, operation mask, factory
result mask and loan-retention permission. Local names are unique across the
consumer package; there are at most 256 imports in total. An empty export path
names the dependency's root export. The export namespace owns non-ASCII policy.
These are requests, not grants. [Composition](05.1-composition.md) approves and
wires access separately; an absent optional dependency supplies no imports. Native `rv_module_import` carries
the same bounded fields, copied before construction with the package metadata.


The Rust owner is `module::Declaration`; native `rv_module` carries the same
fields and a bounded `rv_module_dependency` array. Admission copies and checks
this metadata before construction. Code leases separately retain callbacks.

## Scope and state

Types: [ResourceId](01-resources.md), [caller access](01.2-operations.md)
and [DriverOps](05-runtime.md). Registrar is the Rust view of the scoped
publication capability in [native registration](06.2-native-dispatch.md).

```rust
// Path: kernel/interface/src/module.rs; module: interface::module
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub enum ModuleScope {
    Global, // Shared in this Kernel Runtime; no process-wide singleton.
    Session(ResourceId), // Authorized Session reference in this caller scope.
}
pub struct ModuleContext<Imports> {
    pub instance: ResourceId, // This exact live instance, not a registry alias.
    pub scope: ModuleScope,
    pub namespace: ResourceId, // Its namespace subject; this ID grants nothing.
    pub imports: Imports, // Granted caller access and required public services.
    pub exports: Registrar, // Provisional contributions for this activation.
}
```

`Imports` is a module-defined struct of granted access and optional helpers.
Runtime supplies it after dependency/version/grant checks. The common SDK
also retains request recovery.
IDs and metadata cannot manufacture authority. Activation cannot depend on
looking up its own unpublished exports.

```text
global state   -> shared settings/services within this Kernel Runtime
Session state  -> this editing space's declared module values
live state     -> private implementation objects, tasks and caller access
// A module can request both Session state and explicitly granted global data.
// Reusing code does not share mutable instance state or grants.
```

[Session](04.1-session.md) owns retained context; its schema owner defines
meaning and sharing policy. A Session-scoped Kernel module still executes in
Kernel Runtime. Client extensions may separately access retained Session data
through public APIs. Remote access uses authorized proxies; raw IDs cannot
cross connection namespaces.

State schemas are versioned and separately owned by each module. Adding a
module must not add fields to a concrete Kernel Session struct. Retention
across code unload requires a data form whose storage/destruction needs no
module code; live private objects can instead keep the implementation loaded.
Restoration needs schema compatibility or explicit migration. Retention is
bounded and does not imply disk/crash persistence.

## Implementation contract

`State` is the module's private live implementation type, not Session data.
Both `State` and `Imports` are declared generic parameters here. This is the
same-build Rust factory surface; [native modules](06.1-native-abi.md)
require its binary adapter. Composition pairs the checked declaration, required
export paths and a code-retaining constructor in `module::Definition`. The
registry stores that Interface value without constructing a live instance.

```rust
// Path: kernel/interface/src/module.rs; module: interface::module
pub struct ModuleImplementation<State, Imports> {
    pub construct: fn(
        context: ModuleContext<Imports>,
    ) -> Result<State, (ModuleContext<Imports>, Error)>,
    pub driver: DriverOps<State>, // Runtime pairs this with constructed State.
}
```

Construction creates an inert instance. On rejection, it returns the unchanged
activation context and leaves no installed contribution or external effect.
Fallible external initialization belongs to the driven Starting phase.
The owning Runtime retains State, its declared driver and required code;
the module receives no driver for the containing Kernel Runtime.

Starting stages exports through the activation-scoped registrar. Stage rejection
returns provider ownership. [modprobe](05.3-modprobe.md) owns batch validation,
publication and rollback; either outcome fences this capability and its copies.
Later creation uses [request-scoped staging](06.3-state-providers.md).

The instance reuses [Runtime lifecycle](05-runtime.md).
[modprobe](05.3-modprobe.md) owns activation ordering, contribution publication,
failure and unload. First-party and third-party modules use these entry points.

## Provider contributions

A provider implements operations over private context. Per-instance context
holds state; a vtable holds behavior. One module may contribute several
providers. Provider names that contribution, not a separate module class.

ResourceProvider is the generic owned implementation bundle used for staging.
Concrete constructors and backing types stay in modules or private libraries.
Callers acquire access and invoke declared operations.
[Resource backing](01-resources.md) is opaque to Kernel. Adding behavior
requires no common table field for that backend, server dispatch branch or SDK
method. Byte I/O is optional.

Existing devices can be published or discovered through namespace
materialization. Factories serve declared creation operations. Later device
arrival uses [namespace providers](06.4-io-providers.md), not a reopened
activation registrar.

An ordinary Kernel module can supply Mesh or Map providers. DriverOps is the
[Runtime lifecycle interface](05-runtime.md), not another extension category.

| Table family | Acts on | Purpose |
| --- | --- | --- |
| Namespace | Container/provider instance | Lookup, list, naming mutations |
| I/O | Opened access | Supported stream, positional or packet transfer |
| Execution | Executable Resource | Invoke its bound operation |
| Control | Bound interface | Local ioctl operations |
| Factory | Creation request | Stage Resource, Buffer or watch creation |
| Editing | Selected immutable state | Prepare a candidate for acceptance |

The [native records](06.2-native-dispatch.md) own registration and callable
ownership. [State providers](06.3-state-providers.md) own factory/preparation
callbacks; [I/O providers](06.4-io-providers.md) own open, transfer and namespaces.
Optional tables/methods report Unsupported under [operation selection](01.2-operations.md).
Public getters can use local control methods without a separate executable
Resource per field. Code, instance, open access and request lifetimes differ.

## Pairing, authority and SDKs

A distribution may package Kernel modules with companion Client modules.
Logical service requirements can cross their execution owners. Each owner
uses its own activation API; Kernel registry activation edges select Kernel
instances. Composition coordinates required access across owners without
assuming shared loaders, ABIs or atomic cross-owner activation.
Clients without a local extension system can still use the public service API.
The [Client module direction](09.1-client-modules.md) describes one Client
module serving multiple families through their compatible public interfaces.

Declarations name role/family, compatible imports/exports, required/optional
dependencies, state scopes/schemas, trust and consumed bounds.

Code homes: `extensions/` for contributions, component APIs beside their
owners, `sdk/` for common language access and owning Runtimes for activation.
[Composition](05.1-composition.md) owns API-package dependencies.
[Native/service adapters](06.1-native-abi.md) own binary/language details,
ownership and isolation limits. Portable applicable Rust uses `no_std + alloc`;
native I/O stays in separately granted Host adapters.

The [complete journey](07.2-module-journey.md) shows separate module owners,
shared editing and unload blocked by retained state.
