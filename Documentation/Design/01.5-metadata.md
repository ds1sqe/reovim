# Resource metadata

ResourceInfo exposes Kernel Resource-node metadata: structural
flags and internal atime/mtime/ctime. This applies to every kind of Resource,
including Buffers, commands, GPIO and connections, not just file-like objects.
[Resource access](01-resources.md) owns identity and handles; this chapter owns
structural flags, timestamp updates and their Host clock boundary.

## Structural flags

| Flags | Meaning |
| --- | --- |
| CONTAINER \| EMPTY | Supports children; currently has no visible children |
| CONTAINER | Supports children; currently has visible children |
| Neither | Does not support children |

EMPTY is valid only with CONTAINER. It describes the caller-visible child
listing at observation, not data length. Concurrent changes can invalidate it;
it is neither stable nor authority to delete. READ/WRITE/EXEC and container
mutation rights remain separate.

## Internal times

```rust
// Canonical records; Option uses Choice(None=0 Unit, Some=1 value).
struct ResourceTimes {
    atime: Option<Timestamp>, // Last recorded data access.
    mtime: Option<Timestamp>, // Last recorded data modification.
    ctime: Option<Timestamp>, // Last recorded status change.
}
struct Timestamp {
    seconds: i64,            // Seconds since the Unix epoch.
    nanoseconds: u32,        // Fraction, 0..1_000_000_000.
}
```

ctime means status-change time, not creation time. Creation initializes all
available times, but later status changes overwrite ctime. A separate birth
timestamp would be a different feature, not an alternative meaning of ctime.
These names follow [POSIX stat](https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/sys_stat.h.html);
the Resource-specific update policy below does not claim POSIX conformance.

Kernel owns these fields on the Resource node, shared across handles and names
that refer to that same subject. Access handles have no independent node times.
They are not copied automatically from a native inode or remote server.
Backing/provider timestamps remain separately identified external metadata.
A new copied Resource gets its own times; a new name for the same Resource
does not create another set. Snapshots must identify captured versus live times.

## Update policy

| Authoritative event | Internal time update |
| --- | --- |
| Create Resource | Initialize atime, mtime and ctime |
| Successful data/value read or message receive | atime |
| Successful data write or accepted Buffer state change | mtime and ctime |
| Change owned status/permissions or subject link metadata | ctime |
| Add/remove/rename child entry | Affected container mtime and ctime |
| Passive info/lookup, handle bookkeeping, zero-length byte no-op | None |

Buffer edit/Undo/Redo stamps the newly accepted transition; it does not restore
old timestamps from the selected History state. Atime bookkeeping creates no
Buffer edit, History node or save. Reading metadata must not recursively modify
that same metadata or generate an unbounded diagnostic loop.

Methods declare an allowed activity mask; native outcomes report the subset of
known events that occurred. READ updates atime, WRITE mtime/ctime, STATUS ctime.
Zero reports no event. Runtime validates the mask and applies it once per
original request; reconciliation may add known events without restamping earlier
ones. Core supplies Buffer/History/namespace events itself. A provider cannot
stamp a Buffer edit before acceptance. Common data I/O permits only its
corresponding read/write activity. Metadata queries declare zero activity.

GPIO value reads report READ, known output changes WRITE, configuration STATUS;
socket receive reports READ, known accepted send WRITE, configuration STATUS.
An empty received packet is an access; a zero-length byte no-op is not. Driver
acceptance is not proof of physical voltage or remote processing.

Stamp only known authoritative transitions. Rejected calls do not fabricate data
changes; partial/uncertain effects keep their existing outcome/recovery rules.
Reconciliation must distinguish effect time known at the event from later time
of discovery. Timestamps never establish exactly-once execution.

## Clock and commit boundary

Host supplies time; portable code does not call std or an OS clock directly.
Unavailable time is explicit (None), never a fake epoch value. Host clock info
reports its resolution. Timestamps record Kernel observation time, not an
unobserved external event's occurrence time. Discovery after uncertainty uses
the recovery observation time and preserves that provenance in diagnostics.
Wall time may repeat or go backward: revisions and causal sequence remain the
ordering/conflict authority, not mtime/ctime equality.

Prepare clock observations before Core's commit cut. Applying metadata cannot
introduce I/O, callbacks or new fallible work after state installation.
An unavailable clock sets the affected fields to None; the edit still succeeds.

Default atime policy records actual known access. Any throttling or
disabled-atime policy must be explicit and measured rather than silently added
for performance. It cannot require WRITE rights merely to perform a READ.
