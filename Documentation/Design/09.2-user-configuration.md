# User configuration, settings and input bindings

This [future direction](09-future.md) describes configuration over public
module APIs. Configuration selects implementations, supplies settings and
connects user interaction to exported behavior. A configuration host executes
the user's configuration and applies it through the responsible owners' APIs.
It grants no new Buffer authority or implicit access to other Client contexts.

## Behaviors the configuration surface must express

The design needs both values and programmable policy:

| Behavior | Example |
| --- | --- |
| Defaults and overrides | Wrapping off generally, on for a Markdown view |
| Module settings | Join behavior with a configurable maximum line width |
| Scoped bindings | Close a help view with q without changing normal editing |
| Service-dependent bindings | Offer rename only with a ready supporting service |
| Lifecycle policy | Apply view settings when a matching context opens |
| Conditional selection | Choose an available formatter for the current language |
| Runtime toggles | Change format-on-save through the owning workflow's API |

These needs motivate an eventual user programming language in addition to
declarative values. They do not require compatibility with another editor's
plugin manager, globals, event system or runtime.

## Apply settings at their owner

A setting is a named, typed value accepted by a particular public API. Its
owner defines defaults, validation, supported scopes and when a change takes
effect. Authored document values use the document's edit API even when they
affect appearance.

| Value or policy | Owner and application point |
| --- | --- |
| Map movement step, zoom factor, grid visibility | map-client context/view settings |
| Wrapping, line numbers, view layout | Relevant Client view/presentation API |
| Key sequences, mode/context predicates, chord timing | Client keymap/resolver APIs |
| Format on save | Client save workflow, or an explicitly composed semantic service |
| Map import limits or indexing behavior | Owning Map Kernel module's configuration API |
| Coordinate frame stored in a .map file | Map document content, changed through Buffer edits |
| Device-specific input/output options | Separately granted Host/Client adapter configuration |

Kernel and Client configuration can be authored together; the configuration
host dispatches each change to its actual owner through
[composition](05.1-composition.md). Retaining values in a Session Resource does
not transfer their application or execution to Kernel.

The public settings schema includes type, default, supported scope, constraints
and application timing. Module validation handles semantic constraints, such
as finite positive movement_step or zoom_factor greater than one. A schema is
also usable for help, completion and settings UI. The exact metadata records
remain part of the future [Client module surface](09.1-client-modules.md).

For a setting supporting these scopes, the proposed order is module default,
user baseline, matching Client override, Session override, then specific Map
context/view override. Owners expose only meaningful scopes. Equal-specificity
active declarations conflict unless an explicit priority or replacement
resolves them; source-file order supplies no hidden precedence.

## Activation, context changes and reload

At activation, the host selects dependencies, supplies initial configuration
and validates contributions before publishing ready behavior. On opening or
attaching a context, it applies matching overrides through that context's
owner. A service-dependent binding becomes usable only with a compatible,
ready service and the necessary access.

An explicit toggle or reload calls the owning public settings API. For example,
a formatting toggle updates the save workflow's setting, and the workflow
reads that setting when deciding whether to request formatting. A UI module
does not mutate an anonymous global owned by another module.

Validate replacement settings and bindings before publishing them in the
affected owner's scope. Failed validation preserves that scope's prior usable
configuration. Retiring bindings fences pending input under
[Client resolver rules](04-clients.md). A coordinated change across owners
reports each result; a Client/Kernel-wide atomic configuration transaction is
not implied. Settings that require restart or reopening say so in their schema.
Exact update/callback ordering and per-owner publication cuts remain to be
specified with the configuration API.

```text
// Proposed settings call on an already bound MapClientApi.
// selected_map_context identifies this caller's granted Map context.
map.settings.configure({ movement_step: 2.0, zoom_factor: 1.2 },
                       scope = selected_map_context)
```

## Client filters and input bindings

A Client filter selects the target contexts for a declaration. Family or
presentation labels are convenient selectors; required public interfaces still
determine whether a contribution can run. Filters do not grant access.

The following two forms express the same binding policy. The configuration
host applies each declaration to matching Clients, resolving map to that
target's own ready MapClientApi instance. The call context selects its current
Map context. Key sequence spelling is illustrative.

```text
// MapClientApi comes from map-client's passive API package.
map = modules.require("map-client", MapClientApi)

client.tui.keymaps.bind(["C-t"], map.toggle_grid, when = { view: "map" })
client.gui.keymaps.bind(["SPC", "t"], map.toggle_grid,
                       when = { view: "map" })
```

Equivalent grouped form:

```text
keymaps.bind(map.toggle_grid, {
    client.tui -> ["C-t"],
    client.gui -> ["SPC", "t"],
}, when = { view: "map" })
```

These examples use gui for graphical Clients, including Web; web can select
the Web subset explicitly. Selector names and alias declarations still need
a concrete schema. Matching more than one equally ranked branch reports a
conflict; a narrower-looking label has no implicit precedence.

An omitted Client receives no binding from this declaration. Disabling or
replacing an existing binding is explicit and identifies its owner. Default
bindings are module-owned contributions that users can override through that
same public registration system. Scope/priority/ambiguity behavior remains
owned by [keymaps and resolver](04-clients.md), including pending-chord fencing.

CLI argument parsing can invoke the same exported methods without installing
keymaps. A controller or neural input module can bind its interpreted events
to those methods using its applicable input contract. A Web Client may offer
keyboard, VR and neural input together. Interface-based selection complements
family selectors; [Client modules](09.1-client-modules.md) owns compatibility
and continuous input/presentation behavior.

## Configuration files are Resources

A configuration file uses the ordinary File Resource interface. It can also
be edited through a text Buffer with a source attachment. Those are separate
identities, as in the [Map file journey](07.6-map-journey.md).

```text
configuration File Resource -> text Buffer -> edit -> explicit Save
configuration File Resource -> coherent capture -> explicit load/apply
```

Reading, observing, editing or saving that file does not itself execute its
contents. Startup or an explicit reload selects a coherent saved capture.
If applying an unsaved configuration is supported, the caller explicitly
selects that immutable Buffer snapshot and the host reports which version
was applied. File publication and configuration application have separate
outcomes.

Assembly supplies the bootstrap configuration host and its grants before
executing user configuration. Configuration can then select ordinary modules
through their public activation APIs. This keeps bootstrap independent of an
unpublished module trying to configure itself. Parsing and file-format
handling are private functions of the responsible implementation.

## Language and server-hosted execution

Three choices are independent:

| Choice | Meaning |
| --- | --- |
| Configuration language | What the user writes to select and configure behavior |
| Module implementation language | What implements exported handlers |
| Execution/presentation location | Where those handlers and output run |

Lua, TypeScript and Python are candidates for user configuration. No language,
embedded engine or module implementation language is selected here. Start
with one supported configuration language and a real author-to-behavior
journey. Language-neutral schemas let additional adapters use the same public
APIs; source-language annotations alone do not export a checked runtime schema.

A server-hosted configuration runtime can use Python or another supported
hosted language. Server-side rendering (SSR) keeps presentation under Client
ownership. A Python configuration host does not imply Python code executes in
the browser, nor does the existing Kernel Server SDK supply a Client adapter.
The [release language matrix](../README.md) remains the scope owner.

```text
hosted configuration, for example Python
    -> inspect MapClientApi declarations
    -> choose target Client contexts and supply settings/bindings
    -> each target binds its actual module instance

input -> bound command
    -> execute locally where its implementation is hosted, or
    -> explicit Client transport -> owning hosted Client Runtime
```

Remote declarations carry checked values and command references, not arbitrary
function closures. A local Map command can update its view in its Client
Runtime. A hosted callback stays in its hosting language runtime and needs an
explicit invocation path from the invoking Client. Instance identity, context,
request outcome, disconnect and teardown must be declared for that path;
SSR alone supplies none of those interactive guarantees.

Filter declarations before selecting target-specific executable configuration.
Target and language metadata must be inspectable without evaluating that
target's code. A host must not first evaluate foreign-language code and only
then discard it because its Client filter does not match. Declarative
configuration can be evaluated centrally and distributed; callbacks keep
their actual execution owner. The exact bootstrap language, adapter ABI and
Client transport remain open choices requiring a concrete consumer journey.
