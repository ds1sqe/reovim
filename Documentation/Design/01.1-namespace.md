# Namespace and naming operations

The namespace contains parent/name edges locating [Resources](01-resources.md).
Multiple names may refer to one subject, including supported container links.
Names find subjects; declared interfaces define supported access.

## Names and lookup

```rust
// Path: kernel/interface/src/namespace.rs; module: interface::namespace
use alloc::boxed::Box;

pub struct ResourceEntry {
    pub name: Box<[u8]>, // Owned name bytes; directory entries stay private.
    pub resource: ResourceId, // Copying retains and grants nothing.
}
```

The namespace provider privately owns names, directory entries and indexes.
Paths are queries; returned names are owned values without growth capacity.
Rename changes neither an earlier listing nor an existing ResourceId.

Names and paths are byte sequences restricted to ASCII by default. A namespace
may explicitly opt into non-ASCII names, preserved without conversion or
Unicode normalization. This policy never restricts Resource contents.
SDK paths are absolute, at most 4096 bytes, and use `/`
(byte 0x2f). `/` names the root. Child names reject empty, NUL, `/`, `.` and `..`;
paths reject empty components except the root. Providers preserve native names
through a lossless mapping; opted-in providers may require UTF-8 or retain native
name bytes. Clients own decoding and display. Session-relative CWD/PATH policy
stays above this boundary. Borrowed paths are captured before queuing.

Listings contain unique names and are caller-owned copies, not leases.
Oversized complete listings return pressure or use an explicitly paged
enumeration interface. Resources need not enumerate their data units.
Lookup/listing use ordinary [request outcomes](01.2-operations.md).

## Namespace operations

```rust
impl Kernel {
    async fn create(&self, path: &[u8])
        -> Result<ResourceHandle, RequestError>;
    async fn delete(&self, path: &[u8]) -> Result<(), RequestError>;
    async fn copy(&self, source: &ResourceHandle, destination: &[u8])
        -> Result<ResourceHandle, RequestError>;
    async fn link(&self, source: &ResourceHandle, destination: &[u8])
        -> Result<(), RequestError>;
    async fn rename(&self, source: &[u8], destination: &[u8])
        -> Result<(), RequestError>;
}
```

create uses the parent's declared default child factory and rejects if absent.
It creates one new ordinary data subject plus its name, returning READ|WRITE
access. Provider-specific initializers use typed factory operations, not a
Kernel enum of every module's create payload. No operation creates intermediate
directories, truncates an existing object or silently replaces a destination.

| Operation | Required authority/support | State effect |
| --- | --- | --- |
| create | Parent WRITE and child-creation support | New subject and name |
| delete | Parent WRITE and removal support | Remove selected naming edge |
| copy | Source READ/copy support and destination creation | Independent state/ID |
| link | Source visible to caller, parent WRITE/link support | New name, same ID |
| rename | Both parents WRITE/move support | Move naming edge, retain ID |

WRITE on a container permits supported namespace mutation; it does not grant
WRITE on every object named there. Source references and changed destination
subjects require their own rights. Provider ownership rules can further restrict
publication and removal. A system view such as /sys/module offers no default
user creation, including through another name. No pathname blacklist is used.

Grants are attached to subject identities or explicit ownership scopes.
Namespace ancestry does not define authority. Link/rename neither changes scope
membership nor increases existing handle rights. Namespace entries cannot grant
another caller access just because that caller can list the parent. Composition
must grant intended Session/shared publication scopes explicitly.

delete removes one name, not the subject's shared lifecycle. Nonempty container
removal rejects unless an explicit separate recursive operation is used. Link
never substitutes copying. Links to containers require provider support and
bounded navigation; a navigation cycle is not permanent access ownership.
Cross-Kernel identity linking rejects; a proxy is a separate local subject.

copy captures coherent state before publishing an exclusive destination. Buffer
copy uses the [Buffer copy rule](02-buffer.md), not a blanket rejection. A live
stream without a finite capture rejects copy; its capture operation is explicit.
Container copy does not imply recursive copying of its children. Cross-provider
copy requires supported capture/import and owned rollback; partial data never
appears as a successful complete copy.

rename is no-replace and atomic at the owning namespace boundary. Unsupported
cross-provider movement rejects; it never emulates move by copy/delete. Identity,
parent ownership and destination absence are revalidated at installation. Lost
replies recover the same name mutation, not a fresh operation at the path.
The request retains the subject identity and original/destination locations;
completion evidence records the actual result under
[request custody](01.3-requests.md). An inability to preserve identity requires
explicit copy/publication, outside rename.

## Published names

Composition installs namespace views under explicit caller grants:

| Location | Owner and contents |
| --- | --- |
| /sys/module | Available artifacts and passive declarations |
| /proc/session/{id} | Session identity, lifecycle and granted inspection |
| /proc/session/{id}/env | Session CWD, PATH and environment |
| /proc/session/{id}/module | Session module instances and contributions |
| /proc/client/{id} | Server-side attachment and connection metadata |
| /proc/client/{id}/session | Link to the attached Session, when present |
| /proc/self | Caller-qualified Client record |
| /env | Alias to the attached Session's environment |
| /modules | Alias to that Session's published contributions |

For example, /modules/treesitter/parse locates one declared executable. Input,
output and info may be separate Resources under a connection when their APIs
require separate identities or grants. Ordinary fields, arguments and getters
need no child Resource; control operations can act on the same bound subject.

[Modules](05.2-modules.md) own instance scope; [Sessions](04.1-session.md) own
attachment and environment. Client-local modules, viewports and input state
stay in Client memory/storage. /proc/client exposes server-owned facts and
explicitly reported metadata; it does not host those local modules. Optional
[Client exports](07.5-client-resources.md) have their own granted proxy interfaces.
