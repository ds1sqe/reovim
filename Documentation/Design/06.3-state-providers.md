# State factories, editing and source bindings

This chapter owns provider-facing immutable state, factory, preparation and
backing records. [Editing](02-buffer.md) owns atomic acceptance;
[sources](02.2-sources.md) and [publication](02.3-publication.md) own relationships.
[Domain APIs](07-domain-apis.md) map their values onto these records.

## State is private; snapshots are Resource access

```c
typedef struct rv_state_ops {
    size_t bytes;
    void (*retain)(const void *state);
    void (*release)(const void *state);
    uint32_t (*snapshot)(const void *state, rv_provider *output,
                         rv_error *error);
} rv_state_ops;
typedef struct {
    const void *data;
    const rv_state_ops *ops;
    uint64_t cost;
} rv_state;
```

rv_state is one owned immutable state reference. History and snapshots retain
it explicitly; release runs outside commit guards with its module code pinned.
The same-build Rust owner is `provider::State`. Its clones share immutable data
and code; snapshot providers and their pending requests retain that ownership
after the original State handle is released.
cost is the provider-declared quota charge, not proof of actual memory usage.
snapshot constructs an inert read-only provider over that state, with ordinary
data/control interfaces and deferred reads. It may fail before publication; it
does not wait or perform external I/O. Its provider must offer no mutation.
It transfers ownership on success; errors leave output untouched.

Core does not downcast data or interpret a Mesh/Tree. The originating editing
binding determines valid private state. Adapters preserve that originating
implementation when retaining state; sharing code does not establish private
state compatibility. Importing foreign state uses a declared
factory/transform; a matching pointer size is not compatibility.

## Preparation stages; Core installs

```c
typedef struct {
    const void *before;
    void *context;
    uint32_t (*propose)(void *context, const rv_state *candidate);
} rv_edit;
typedef struct rv_edit_ops {
    size_t bytes;
    uint32_t (*prepare)(void *context, uint32_t command,
                        const rv_edit *edit, const rv_args *input,
                        rv_pending *output, rv_error *error);
    uint32_t (*write)(void *context, const rv_edit *edit,
                      const rv_write *input, rv_pending *output,
                      rv_error *error);
} rv_edit_ops;
```

Runtime supplies selected before state and a request-scoped staging capability.
Same-build Rust providers receive `provider::Edit` through
`ProviderInterface::prepare`. `before()` borrows selected State; `propose()`
uses the request owner's candidate-retention callback.
prepare follows native begin/poll/take/cancel/finish rules. A successful propose
retains the candidate in the request; the provider still releases its own owner.
Only one candidate may be staged. Failure leaves ownership unchanged. The edit
view remains valid through preparation; it grants no general installation API.
The provider cannot propose from an unrelated ordinary ioctl/exec request.

An OK result with a staged candidate requests acceptance; an OK result without
one is an explicit unchanged/read result. Propose requires WRITE on the target.
Runtime validates output values/references, currentness, grants and capacity
before Core installs state/History. Failure/cancellation discards staged state
outside guards. No callback, allocation or I/O follows the commit cut.
The accepted BufferState is host-owned result metadata alongside the declared
value, so Core does not patch a domain-specific payload to insert a revision.

An editing API is registered with rv_edit_ops instead of ordinary control ops.
Its local ioctl commands still use InterfaceDecl inputs/results. Read controls
receive immutable selected state but cannot propose without declared WRITE.
Standard byte writes on Buffers use this preparation owner, return an accepted
prefix count and never mutate through a separate live-state callback.

## Factory installation

```c
typedef struct {
    rv_state initial;
    rv_provider implementation;
    const rv_edit_ops *byte_edits; /* Optional standard byte-write binding. */
} rv_state_init;
typedef struct {
    size_t bytes;
    uint32_t (*refresh)(void *, const rv_edit *, const rv_args *,
                        rv_pending *, rv_error *);
    uint32_t (*publish)(void *, const void *state, const rv_args *,
                        rv_pending *, rv_error *);
} rv_backing_ops;
typedef struct {
    rv_state_init state;
    rv_args attachments;
    const rv_backing_ops *backing;
} rv_buffer_init;
typedef struct {
    uint32_t (*keyed)(void *, rv_bytes key, const rv_provider *);
    void *context;
    uint32_t (*resource)(void *context, const rv_provider *provider);
    uint32_t (*buffer)(void *context, const rv_buffer_init *initial);
    uint32_t (*retained)(void *context, const rv_state_init *initial);
    uint32_t (*auxiliary)(void *context, const rv_provider *provider,
                          rv_access *provisional);
} rv_creation;
typedef struct rv_factory_ops {
    size_t bytes;
    uint32_t (*create)(void *context, uint32_t command,
                       const rv_creation *creation,
                       const rv_args *input, rv_pending *output,
                       rv_error *error);
} rv_factory_ops;
```

A factory is declared Exec or Ioctl with Factory dispatch. Exec passes command
zero; a creating ioctl passes its declared number. Runtime supplies one staging
target with caller ownership and optional destination naming. The factory stages
exactly one primary target; OK without one rejects as Provider error. Staging
validates/copies descriptors and retains required owners; it never publishes
immediately. Failure leaves the supplied owner with the provider. On success
provider contexts transfer; state references are retained, and the supplying
provider releases its original state reference. The same rule applies to
auxiliary/open staging. Successful creation publishes atomically with
host-created access plus the factory's declared auxiliary result.

Initial access runs any offered Open before installation, including returned
new auxiliaries. All returned accesses remain private until the batch is ready.
After creation succeeds, failed initialization retains the original result for
reconciliation. A retry initializes only the failed access after cleanup; it
never repeats creation or earlier successful initializations. Uncertain Open
reconciles its original pending operation. Rejected batches drain opened
contexts before their staged subjects.

Auxiliary providers can supply additional declared owned output references, such
as an observation's snapshot. They remain provisional in the producing request
until the same creation batch commits. Unreturned or rejected auxiliaries are
cleaned up outside guards; they cannot leak into another caller's namespace.
Buffer initialization stages state, editing bindings and attachments together.
Namespace create uses keyed staging to reserve a new object key and provider
as one primary target before publishing the name; rejection transfers neither.
The installation owner copies the key, rejects a live-key conflict and prevents
another materializer from installing that key until creation settles. Ordinary
resource staging cannot substitute for this association. Existing-object
materialization already holds its selected key and uses resource staging.
Namespace create invokes the parent's configured factory; BufferService.create
uses its configured Buffer factory. An explicitly selected factory is invoked
through its declared exec/ioctl. Factories take typed initializer/source sets,
including repository entries.

state.implementation owns interface contexts and their stop/destroy lifecycle.
Its edit tables operate on selected state; byte_edits, when present, uses its
write callback and that same context. No Buffer registers a live io.write.
Absent byte_edits means unsupported byte writing, including on non-byte state.

## Backing callbacks

[Source relationships](02.2-sources.md) define source entries and the
canonical rv_buffer_init.attachments value. [Publication](02.3-publication.md)
owns target policy, conditional effects and saved/base bookkeeping.

backing callbacks use implementation.context and ordinary pending ownership.
refresh receives an rv_edit and {sources, policy}; it stages one candidate.
publish receives immutable selected state and {targets, policy}. Each target
is {key:Utf8, destination:Ref(AnyResource,WRITE), base:Option<Ref(READ)>}.
The Runtime acquires/revalidates these references before calling the provider.
Missing callbacks return Unsupported. Provider mappings and conditional target
updates run outside Core; the provider cannot mark Buffer bookkeeping saved.
publish returns ordered {key, destination:Identity, outcome} records. Outcome
is Applied{base:Option<Ref(READ)>}, Conflict, Unsupported or Unknown{detail}.
Each input target has one result; unknown work retains the original pending
context for reconciliation. Any unknown target makes the native outcome UNKNOWN;
its progress report contains no output references. Final OK returns owned bases.
Known applied outcomes cannot later regress or be applied a second time.
Runtime updates evidence only for the captured attachment generation and state.
An intervening detach/edit cannot mark a new association or later state saved.

## Session and cleanup

Session context uses the same immutable state/preparation owner with its own
revision/reference installation, not Buffer History. Its factory/interface is
module-owned; creation.retained stages this state without Buffer History.
Stop, state release, shared Buffer close, attachment detach and
request finish are separate lifecycle actions. All incomplete cleanup remains
under the original Runtime/service owner with bounded admission accounting.
