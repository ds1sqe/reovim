# Client modules, schemas and execution

This [future direction](09-future.md) describes the Client module authoring
surface. A Client module supplies interaction and presentation policy through
public Client APIs. CLM refers to this Client-owned module concept. Its owning
Client Runtime executes it and retains its live state and contributions.
[Clients](04-clients.md) owns the underlying responsibility boundary.

## One module across Clients

One map-client module serves CLI, TUI and Web through compatible public Client
interfaces. It owns one public API and shared command/state behavior. Its
presentation and input helpers can vary with the available interfaces while
remaining parts of that module. Separate modules per Client family are not a
requirement.

Support follows the interfaces each contribution requires. A closed list such
as clients: [cli, tui, web] cannot establish compatibility. A new Client can
use existing behavior when it provides the required contracts; a new rendering
or input contract may require additional implementation in map-client.
Optional contributions declare their unavailable behavior. Required interface
loss follows [Client readiness](04-clients.md).

| Contribution | Required support |
| --- | --- |
| Movement and zoom commands | Command invocation and a selected Map context |
| Default keyboard bindings | Keymap and logical-key interfaces |
| Textual Map summary | Bounded structured/text output |
| Terminal Map view | Supported cell or graphics presentation |
| Web Map view | Supported graphical presentation |
| Tracked immersive view | Spatial input and suitable spatial presentation |

A Map context is module-owned state for a particular use of a Map Buffer,
including camera and view settings when applicable. A CLI can create a context
for a one-shot render or summary without having an interactive viewport.
Its invocation must select the intended context; it does not implicitly change
another Client's camera.

One module definition permits multiple instances and multiple Map contexts.
Each owning Runtime retains its instances; camera, selection and pending input
stay specific to their context unless sharing is explicitly configured under
the [Session/sharing contracts](04.1-session.md). Sharing code or a Buffer does
not merge that state.

## Code and contract locations

Illustrative contribution homes:

```text
extensions/map/api/         # Kernel Map types and operation declarations
extensions/map/kernel/      # File format, factories, snapshots and edits
extensions/map-client/api/  # Public Client methods and settings schema
extensions/map-client/src/  # Shared handlers, context and output helpers
clients/<family>/contract/  # Public input, commands and output interfaces
clients/<family>/{core,runtime}/ # Contract enforcement and module execution
host/                      # Native device, filesystem and display adapters
```

Client families implementing the same public contract share its declaration
at its API owner. The concrete home for shared Client contracts should follow
the first real consumers; it does not require another execution layer.
Interested extensions import Map APIs. Common Client, Kernel and server code
use neutral contracts, as required by [composition](05.1-composition.md).

A provider is an implementation contribution supplied by a module. It is not
another module category. [Kernel module terminology](05.2-modules.md) owns
provider tables and Runtime DriverOps. Client modules use their own declared
activation interfaces; they do not inherit the Kernel module loader or ABI.

## Export a schema and bind its implementation

A schema is inspectable data describing an exported API's methods and values.
The module's API package owns it and optional typed helpers. Reading a passive
declaration does not activate the implementation. No separately activated
schema module is needed.

Reuse [API identity and checked value declarations](06-declarations.md) where
applicable. Matching uses the API key and full declaration; a method name is
useful for configuration and help but has no implicit dot-path dispatch rule.
Client registration and invocation remain Client contracts. Their exact
records, results and settings metadata need specification before an SDK.

This sketches an author-facing declaration, not the complete ABI record.
MAP_CLIENT_API_ID and MAP_CLIENT_MODULE_ID stand for owner-supplied opaque
keys. F64, Bool and Unit use the common value types. Delta is an XYZ offset
in the [Map journey's](07.6-map-journey.md) world frame; BufferState is the
accepted edit result. MapSettings declares the setting metadata described in
[configuration](09.2-user-configuration.md).

```text
Delta = Record(dx: F64, dy: F64, dz: F64)

export MapSettings = {
    movement_step: { type: F64, default: 1.0, scope: "map-context" },
    zoom_factor:   { type: F64, default: 1.2, scope: "map-context" },
    show_grid:     { type: Bool, default: true, scope: "map-context" },
}

export MapClientApi = {
    id: MAP_CLIENT_API_ID,
    settings: MapSettings,
    methods: {
        move_camera:          (Delta) -> Unit,
        move_selected_object: (Delta) -> BufferState,
        zoom_in:              () -> Unit,
        zoom_out:             () -> Unit,
        toggle_grid:          () -> Unit,
    },
}

export declaration = {
    module: MAP_CLIENT_MODULE_ID,
    name: "map-client",
    exports: [MapClientApi],
    // Imports name complete required/optional public API declarations.
}

activate(ctx):
    state = MapClientState(ctx.imports, ctx.settings)
    api = ctx.exports.provide(MapClientApi, {
        move_camera: state.move_camera,
        move_selected_object: state.move_selected_object,
        zoom_in: state.zoom_in,
        zoom_out: state.zoom_out,
        toggle_grid: state.toggle_grid,
    })
    ctx.commands.register(api.move_camera, context = "map")
    ctx.commands.register(api.move_selected_object, context = "map")
    ctx.commands.register(api.zoom_in, context = "map")
    ctx.commands.register(api.zoom_out, context = "map")
    ctx.commands.register(api.toggle_grid, context = "map")
    return state
```

ctx is this module's granted activation context. Its registrations are
provisional until required services, settings and contributions are ready.
MapClientState and its handlers are private implementation code. The Client
invocation contract supplies qualified context separately from the method's
arguments; each handler resolves its own Map state from that context.

The module validates finite movement values, positive movement_step,
zoom_factor greater than one, and resulting camera limits. Method numbers,
call bounds, context qualification and typed failure/result records must be
fully declared before this sketch can become a checked public API.

Binding follows this sequence:

1. Select a module and inspect its passive exports and imports.
2. Check required declarations, supported contributions and granted access.
3. Activate the selected implementation under the owning Client Runtime.
4. Bind its provided handlers to the declared API and publish ready exports.
5. Retain the exact instance/registration for calls and installed bindings.

The owner retains pending work and registration lifetime. Removal fences new
use and pending input; admitted work keeps its required context/code until
settled. Replacement by the same name cannot retarget old bound commands.
[Client keymaps](04-clients.md) owns resolver precedence and fencing.

Local export discovery does not require a Kernel Resource for every method.
Optional [Client Resource exports](07.5-client-resources.md) can provide a
separately granted remote surface; their transport and reconnect rules remain
their own protocol work.

## Commands and semantic operations

A user-facing command connects interaction to behavior in a selected Client
context. Registering an exported method as a command makes it available to
keymaps, menus, command palettes or CLI policy. An API can also expose methods
that are not user commands. Callable APIs and schemas exist on both Client
and Kernel modules.

```text
key / button / CLI invocation
    -> map-client.move_selected_object(delta)
    -> resolve selection and destination against the displayed snapshot
    -> Buffer.edit(expected_snapshot, MoveObject { id, to })
    -> Map Kernel provider prepares state -> Core commits Buffer + History
```

zoom_in changes Client camera state and requests presentation. Moving a stored
object uses the semantic edit path in the [Map journey](07.6-map-journey.md).
An authorized caller with complete semantic arguments can call that Kernel
operation directly without a Client command registration.

In user configuration, map is a bound MapClientApi on a selected module
instance. map.zoom_in refers to its exported behavior. A string such as
"map.zoom_in" is only optional lookup syntax resolved to that binding; neither
an undefined map.action nor a global action namespace is required.

## Physical hosting and languages

Client describes responsibility and execution ownership. Its Runtime can live
in a terminal application, a browser, or a server-hosted Client service. A
server-side renderer remains Client-owned under [presentation](04-clients.md).
The Kernel service adapter only serves its declared Kernel requests; sharing
a process does not give it ownership of Client commands or rendering.

A single module definition does not guarantee one executable artifact works
in every runtime. Compatible Client/language adapters must supply the actual
execution path. Shared logic and private output helpers can still belong to
one map-client module. Choose artifacts and adapters from concrete consumers;
the [release matrix](../README.md) remains unchanged.

[User configuration](09.2-user-configuration.md) separates configuration
language, implementation language and presentation location. Server-side
rendering alone does not determine where interactive commands execute.

## VR and neural interfaces

Virtual reality (VR) can be a dedicated Client or a presentation/input mode of
a Web or native Client. A neural input interface can supply input to any of
those Clients. A complete neural interaction application could itself be a
Client. These categories can overlap; they are not a closed family enum.

```text
keyboard / controller / neural device
    -> Host adapter supplies device data
    -> Client input modules interpret events
    -> configured bindings select map-client commands
    -> Client context change or an explicit Kernel semantic operation
```

Neural decoding, when needed, belongs to its input implementation. Map commands
consume the resulting configured actions and arguments, not raw neural data.
Native handling belongs in Host adapters; interpretation and binding policy
remain in Client code. No new driver/module category is required.

Commands cover discrete actions. Continuous pose updates and frame production
also use public Client interfaces. Spatial support needs declared positions,
orientation, coordinate frames, timing, bounds and input-loss behavior; an
immersive view needs suitable presentation, such as per-eye output. Existing
zoom handlers alone do not implement those contracts. Their exact records
remain open until a concrete Client and module journey uses them.
