# 05.1 — Composition and wiring

Composition selects implementations and supplies granted
[Resource access](01.2-resource-access.md). Upper layers import Interface and
the public contracts they use. Imports describe calls; actual caller access
selects a running Runtime and its authority.

## Dependencies and contract ownership

```text
apps/assembly -> selected Kernel, Host and initial provider implementations
Kernel Runtime -> Core -> Interface -> Foundation
Clients/Kernel modules -> Kernel Interface + required public component APIs
Client extensions -> their Client contracts + granted public service APIs
Resource/Domain/Representation implementations -> public provider contracts

representation/markdown -> domain/text/api
domain/text/implementation -> domain/text/api
domain/text/api -> kernel/interface
// Source dependencies: Runtime calls providers without importing their crates.
```

| Contract owner | Declares |
| --- | --- |
| kernel/interface | Common access, Buffer/History/Session values, provider and lifecycle contracts |
| Component API | Its Resource, Domain or Representation schemas and optional typed helpers |
| clients/<family>/contract | Input, commands, views, rendering and output |
| Implementation | Private storage, algorithms and execution context |

A new Domain/schema adds no concrete Kernel type. Module helpers encode the
same common requests as generic tools; they are optional consumer code, not
another access lifetime. Loading a new surface needs no common SDK field or
Kernel recompilation. Kernel never imports Client presentation contracts.

A logical dependency names its contract/version, owner and scope. Composition
selects a compatible provider; ambiguous choices reject. A Client module may
require a Kernel service or another Client module's API. Each owner activates
its own instance. Required services must be ready before the dependent feature
is published; optional absence has declared behavior.

## Construct and activate

```text
assembly:
  construct Core and Runtime with selected configuration
  supply separately granted Host services and the module loader
  register initial declarations/providers through public contracts
  retain DriverOps; arrange progress and Host wakeups
  supply consumer access after required startup reaches Ready

modprobe:
  resolve exact contracts, versions and Session/global scope
  load implementation through the Host adapter
  supply ModuleContext with namespace and granted dependency access
  construct and drive the instance; publish ready contributions
// A Client's extension loader is separate from this Kernel modprobe API.
```

Core and Runtime are selected at assembly. Resource, State Model, Domain and
Representation providers can arrive while that Kernel runs. The portable
Kernel is a library with no process singleton or required native event loop.
Replacing live Core authority needs a separate state-transfer contract.

These source layers describe the reference implementation. Independent C or
other implementations may use different internals while preserving the same
[public behavior and ABI/protocol](00-overview.md). Documented use must need
no official-only import or service message.

[Module construction](06-modules.md) owns activation inputs and its driver;
[modprobe](06.2-modprobe.md) owns resolution and teardown. Grants cover declared
contributions, not every service or another module's private state.

An authorized coordinator may load a Client dependency. Lookup, observation
and help display never load code implicitly. Losing a required service fences
old work and makes its dependent feature unavailable. Closing one Client's
access releases its use, leaving shared providers under their owner.

## Call and dispatch

```rust
// Proposed SDK; history is an optional helper using this caller's access.
// The helper encodes the public History contract, not a provider's internals.
let change = history.undo(buffer.history, &buffer.state).await?;
```

```text
consumer -> caller access -> Runtime -> selected provider -> result
// Resolve finds identity. Each request checks method, contract and grants.
// Runtime captures the exact provider and inputs before queuing execution.
// The SDK awaits and adopts the result; dropped waits do not cancel effects.
```

Consumers import neither Runtime nor Core. New providers use the same dispatch
path; names cannot retarget captured work. An unknown schema needs its public
encoding, not a new Kernel type or mandatory module-specific SDK package.

## Provider tables

Interface declares executable tables for adapters. `Context` below is the
provider's private state; only composition/Runtime pairs it with its table.
This same-build Rust sketch uses a standard Future for deferred execution:

```rust
// Path: kernel/interface/src/provider.rs; module: interface::provider
use alloc::boxed::Box;
use core::{future::Future, pin::Pin};

pub type ProviderReply =
    Pin<Box<dyn Future<Output = Result<Message, Error>> + 'static>>;

pub struct ResourceOps<Context> {
    pub read: fn(&mut Context, ResourceId, Message) -> ProviderReply,
    pub write: fn(&mut Context, ResourceId, Message) -> ProviderReply,
}
```

The callback captures owned input/state before its short context borrow ends.
Runtime drives the Future and retains the selected code through callbacks,
work and result destruction. The caller's await never drives the provider.
Method-specific profiles define watching and closing access; this table does
not prescribe one cursor or storage model. Unsettled effects return their
contract's result Message with recovery, never an error that loses evidence.

This table illustrates dispatch, not a required allocation strategy or native
layout. [Native/service adapters](06.4-native-modules.md) preserve ownership
through their negotiated ABI/protocol; Rust Futures never cross that boundary.
Runtime's compiled type cannot enumerate loaded providers. New working state
uses the [State Model boundary](06.1-providers.md), not a closed Kernel enum.

## Editing and user interaction

```text
Client input -> Client command -> qualified semantic edit
Runtime -> Domain/Representation/State Model preparation
Core -> revalidate and atomically install Buffer + History
Runtime -> result/observation -> Client response and rendering
// Representation produces semantic data; Clients decide how to present it.
```

[Editing](03.2-editing.md) owns the commit cut. No provider callback, wait,
fallible work or retired-value destructor runs under that authority. General
Resource I/O remains available; all user-view I/O belongs to
[Clients](04-clients.md). The [complete journey](07.1-module-journey.md)
connects module loading, two Clients, editing and teardown.
