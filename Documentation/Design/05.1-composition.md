# Composition and wiring

Composition selects implementations, pairs contexts with operation tables and
retained code, and supplies granted [Resource access](01.2-operations.md).
This chapter owns source dependencies and wiring. Runtime owns activation and
execution.

## Dependencies and contract ownership

```text
apps/assembly -> selected Kernel, Host and module entries
Kernel implementation (Runtime + Core) -> Interface
consumer -> language adapter -> C ABI <- implementation adapter
common Clients/Kernel/server/SDK -> Kernel Interface
Client core/runtime -> their Client contracts
Kernel/Client extension modules -> Interface + required public component APIs
Client extensions -> their Client contracts + granted public service APIs
Resource/Domain/Representation implementations -> public provider contracts

representation/markdown -> domain/text/api
domain/text/implementation -> domain/text/api
domain/text/api -> kernel/interface
// Source dependencies: Runtime calls providers without importing their crates.
```

| Contract owner | Declares |
| --- | --- |
| kernel/interface | Common access, Buffer/History/Session values, provider and lifecycle contracts |
| Component API | Its Resource, Domain or Representation schemas and optional typed helpers |
| clients/<family>/contract | Input, commands, views, rendering and output |
| Implementation | Private storage, algorithms and execution context |

Common Kernel/server/SDK/base Clients import no domain API package. Extension
providers and interested Client modules own those dependencies. Client
core/runtime use their own presentation contracts; Kernel/server/common Kernel
SDK do not import them. API packages contain declarations and optional wrappers,
not selected implementations or global contexts. A new domain adds no common
SDK field, dispatch case or access lifetime. Generic callers use declarations
and checked values; [domain examples](07-domain-apis.md) show typed users.

A logical dependency names a module selection and complete API declarations.
Composition selects a compatible provider; ambiguous choices reject.
[Import requests](05.2-modules.md) identify exact dependency exports and requested
rights. Registration explicitly approves local names from the immutable package
declaration, granting each approved request's exact rights. Validate the complete
offered API before constructing the consumer; a Ready dependency grants nothing.
Each selected activation derives its own Caller from composition grants and its
approved dependency exports. `/imports/<name>` resolves in that Caller alone;
missing local imports never fall back to ambient paths under that prefix.
Inert construction cannot submit through this Caller. Retained clones are fenced
if construction rejects. Keep successful import grants through requests, provider
cleanup and module destruction, then fence and drain the context before releasing
its capacity and dependency use. Runtime shutdown preserves that same order. A Client
module may require a Kernel service or another Client module's API. Each owner
activates its own instance. Required services must be ready before the dependent
feature is published; optional absence has declared behavior.

## Assembly

```text
assembly:
  construct Core and Runtime with selected configuration
  supply separately granted Host services and the module loader
  select initial module declarations and artifact/linked entry points
  activate modules through their lifecycle and scoped publication registrar
  retain DriverOps; arrange progress and Host wakeups
  supply consumer access after required startup reaches Ready
```

Core and Runtime are selected at assembly. Resource, factory, editing and
semantic providers can arrive while that Kernel runs. The portable
Kernel is a library with no process singleton or required native event loop.
Replacing live Core authority needs a separate state-transfer contract.

A Host loader can offer declared Exec(Bytes path) -> ResourceId admission in a
configured registry/mount. Composition supplies artifact-selection/ABI-trust
policy, immutable module imports, approved dependency names and one recipient.
The operation grants that recipient package access; it does not activate code or
grant exports. Provider callbacks only queue; composition drives admission outside
Runtime callbacks and registration guards. Original request custody owns delivery.
Paths are native bytes, not text. A retained path selects its exact admitted
package on later requests, never changed artifact contents. Bounded admission
failure preserves any registered package identity as diagnostic context if the
recipient grant fails. Activation remains the package's [declared call](05.3-modprobe.md).

Concrete extension constructors belong to modules or their private libraries.
Boot may select linked module entries; they use the same activation/publication
contract as loaded artifacts. Kernel-owned identity, requests and installation
remain in Kernel. [Modules](05.2-modules.md) own provider construction.

Adding a Resource implementation or declared API requires no source changes or
recompilation of Kernel, common server or base Clients. New artifacts load into
the running system. Clients bind offered declarations; new semantic policy or
presentation belongs to their extensions. Discovery alone supplies no semantics.

These source layers describe the reference implementation. Independent C or
other implementations may use different internals while preserving the same
[public behavior and ABI/protocol](00-overview.md). Documented use must need
no official-only import or service message.

[Module construction](05.2-modules.md) owns activation inputs and its driver;
[modprobe](05.3-modprobe.md) owns resolution and teardown. Grants cover declared
contributions, not every service or another module's private state.

An authorized coordinator may load a Client dependency. Lookup, observation
and help display never load code implicitly. Losing a required service fences
old work and makes its dependent feature unavailable. Closing one Client's
access releases its use, leaving shared providers under their owner.
Composition may grant a newly admitted Resource to an existing Caller without
replacing its receipts or opened access. Repeating the exact grant is idempotent;
changing existing authority rejects. Registered or live module import bindings
cannot be extended: their captured inputs must not change through later loading.
Composition may explicitly grant module publications at an exact activation
mount identity and Global/Session scope. Runtime records each contribution's
membership during staging; an unrelated subject at a similar path is not a
member. This authorizes current and future members without changing naming
rights. The grant retains its scope owner; acquisition retains a member.
An exact subject grant takes precedence on fresh acquisition. Existing opened
access keeps its captured ceiling. [Namespace](01.1-namespace.md) owns the
independence of names and authority.

Composition may retire a caller binding independently of Runtime. Live module
or pending activation imports reject retirement before fencing. Otherwise it
fences new admission and releases its grants only after admitted work and
cross-caller import uses drain under [request custody](01.3-requests.md).

The [module journey](07.2-module-journey.md) connects assembly, separate Client
extensions, two views of one Buffer and provider teardown.
