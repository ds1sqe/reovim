# 07.2 — Services from observations

## Session-driven services

Clients and Kernel modules consume the same public observation contracts.
An event describes a change; an authorized consumer decides whether to invoke
another operation. Observing or resolving a Resource never implicitly loads
code. [modprobe](06.2-modprobe.md) remains an explicit operation.

The same model connects modules: a structure provider invalidates navigation
data; a Client module observes readiness or another Client module's command
context. [Navigation and motion help](06.3-module-composition.md) combines
these feeds with direct read queries and Client-owned presentation.

```rust
// Proposed SDK; language-support has granted Session/Host service access.
// session_context and participation come from its granted Session access.
// Optional stream helper consumes SessionFollow.current/watch; gaps are errors.
let mut follow = session_context.follow_stream(participation).await?;
while let Some(context) = follow.next().await? {
    // Baseline, then updates.
    let selected = context.state.active_buffer;
    services.switch_buffer(selected.as_ref()).await?;
    // On change, detach/fence prior use; None leaves no selected service use.
    let Some(buffer) = selected else { continue };
    let support = services.inspect(&buffer).await?; // Semantics and workspace.
    services.ensure_git(&support).await?; // Only if applicable and authorized.
    services.ensure_rust_lsp(&support).await?;
    services.ensure_source_watch(buffer).await?; // Feed actual unsaved state.
}
// ensure reuses compatible services/watches; it starts no process per event.
```

The module owns detection/autoload policy and granted Host process/service
access. Source support and workspace metadata decide applicability; Kernel
contains no file-extension switch or Rust-specific behavior. Shared services
retain explicit users and observe unsaved Buffer state, not only disk changes.
Diagnostics/results identify the Buffer and analyzed state; stale responses
cannot overwrite current semantic results or edits.

Watch the Session's context when following its selected Buffer. Resolving a
moving Buffer alias once would keep watching the old subject after selection
changes. The future `sessions/{sid}/buffer` surface therefore exposes a
stable context Resource. On switching, release the old subscription/service
use and fence its late delivery. Gap requires coherent refollow/resync; a
service with no recovery contract must report unavailable instead.

## Cross-client protocols

Shared Session/participation Resources can carry versioned presence, focus,
diagnostics or other agreed protocol state. Providers define writes/requests;
[Observation](03-observation.md) supplies independent subscriptions. Each schema
owns authority, ordering, conflict rules and retention, as in
[Client collaboration](04-clients.md).

The [future Client exports](07.3-client-resources.md) illustrate debugger
access, notification submission and watching peer focus. Each receiver maps
semantic focus to its own view and renders locally. Correlate request/result
identity where a protocol needs acknowledgement; an observed event alone
does not settle an admitted operation. Carry origin to avoid feedback loops.

## Before-save work

```text
Session context changed -> language service may start/reconfigure
Buffer state changed   -> LSP/Git service may refresh derived information
Peer focus changed     -> receiving Client may follow and render
Save requested         -> await formatting -> accept edit -> publish that state
// First three are reactions; the last is an explicitly ordered operation.
```

A watch cannot delay or veto an operation already admitted elsewhere. Required
formatting belongs to the [awaited save workflow](03.3-publication.md),
which owns ordering, errors and cancellation. It must not rely on a listener
racing publication, block Core acceptance or turn every event into a hook.
