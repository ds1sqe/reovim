# 01.3 — Interrupted requests and retained work

Ordinary calls [await results](01.2-resource-access.md). If a save or GPIO pulse
executes but its reply is lost, submitting again may repeat the effect.
Request identity and its recovery owner must survive that lost reply.

```text
request -> rejected                    // Never admitted.
        -> running -> result/error     // Runtime drives execution.
                   -> reply lost       // Outcome unknown to this caller.
recover original request -> retained outcome or explicitly missing evidence
// Recovery observes/reconciles this work; it never submits the effect again.
```

## Recover the original request

Before transmission, the SDK reserves correlation and a recovery locator in
a resumable, granted caller scope. Admission records that identity with the
method, contract, encoded input and retained target/reference identities.
Retries join that work/result; any changed input or read/write method rejects.
Reconnection compares owner-side identities, never new connection numbers or
re-resolved aliases. No first reply is needed to identify uncertain work.
Admission reserves required completion/recovery capacity. Passive reads need
only bounded correlation unless results or ownership require retention.

The locator names one Runtime lifetime, caller scope and request. Namespace
management is private; these locators are never rebound or reused. After
reconnect, restore authorized access to that scope and resolve the locator
to a fresh local ResourceId. Old numeric IDs cannot cross connections.
Possession of a locator grants no access. A lost scope or restarted Runtime
can report unavailable evidence; this contract promises no crash persistence.

```rust
// Proposed SDK; request and output are supplied under their public contract.
let reply = match kernel.write(output, &request).await {
    Ok(reply) => reply,
    Err(RequestError::Unknown { recovery, .. }) => {
        // Reuse live access, or reconnect to the same caller scope first.
        let work = kernel.resolve(&recovery).await?;
        requests.result(work).await?? // Outer: read; inner: original outcome.
    }
    Err(error) => return Err(error),
};
// requests is an optional common helper over retained-work Resource access.
// If recovery also fails, keep recovery access; do not discard its owner.
```

The SDK retains unresolved locators when `?`, timeout or a dropped wait ends
the caller's path. Caller access exposes its pending/recovery Resources for
later inspection and transfer. The required locator in RequestError::Unknown
is independent of optional Error.id diagnostics. After safe result adoption,
the SDK retires ordinary request records while preserving required retry or
recovery evidence. Callers close separately returned access Resources.

Missing evidence never proves non-admission. Only an authoritative rejection
does. Request/result retries cannot create another watch, duplicate a returned
lease or consume the next event. SDK correlation includes result delivery and
reference adoption, not just submission.

## Work is a Resource when it needs an independent lifetime

Deferred work and recovery expose ordinary Resources. Their common profile
defines these operations; helpers use the same read/write access:

| Access | Meaning |
| --- | --- |
| read status | Pending, finished or unknown, with cause/evidence if available |
| read result | Await/read the original request's result and effect evidence |
| write reconcile | Recover evidence for this request without repeating effects |
| write cancel | Request cancellation; report requested or already finished |
| close | End retained work access after settlement or transfer to a recovery owner |

The result helper returns `Result<Result<Message, RequestError>, RequestError>`:
outer failure belongs to retrieval; the inner value is the original outcome.
Reconciliation may refine effect evidence; earlier messages stay unchanged.
Repeated retrieval refers to the same result/access ownership; it
cannot manufacture another independent returned Resource. Released/expired
results report unavailable. Returned snapshots, Sessions and other access
Resources survive work close under their own owners.

Cancel is not rollback and does not prove work stopped before acceptance.
Dropping a wait cancels no admitted effect. Reconcile may remain pending or
unknown; repeated requests join existing reconciliation. Denied/unsupported
recovery leaves previous evidence intact. A settled error also
does not authorize replay; it need not prove the absence of all effects.

For [publication](03.3-publication.md), a received result can itself report an
unknown/partial external effect and carry recovery. That differs from losing
the reply. An observation or diagnostic event cannot settle either condition.

## Retention and execution

Runtime owns admitted work and the exact provider through queued execution,
callbacks and result destruction. Provider replacement cannot redirect it;
unload waits for these uses. Completion polling is observation, not an executor.
[Runtime](05-runtime.md) drives providers outside Core commit authority.

Owners bound retained results, subscriptions and recovery records. Expiry is
explicit: an expired record is unavailable evidence, not permission to retry.
Unresolved effects keep a recovery owner through disconnect/close or transfer;
if that cannot complete, shutdown reports incomplete rather than dropping
ownership. Releasing a name never performs this cleanup.
